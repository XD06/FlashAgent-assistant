## 问题复盘：`read_file` / `edit_file` 在 Git Bash 下的出错分析

### 错误 1：`edit_file` 提示 "must match exactly once"

**现象：**
```
错误：old_text 必须恰好匹配一次（找到 0 次匹配）
```

**我给的 `old_text` 用 `\n` 换行，但文件实际是 `\r\n`（Windows CRLF）。**

**根因：**
- Git Bash 默认 `core.autocrlf` 为 `true` 时，`git clone/checkout` 会把文件换行符转为 `\r\n`
- 我的 `old_text` 参数只包含 `\n`，与文件中的 `\r\n` 逐字对比失败
- 工具是**逐字节精确匹配**，不存在智能换行符转换

**具体命中场景：**
1. 改 `addLog` 时 — 我给了 `\n` 结尾的代码块，文件是 `\r\n` → 匹配失败
2. 改频率限制时 — 同样的问题，我改为用 `sed` 绕过
3. 模板文件的 `/api/logs` 修改 — 同样遇到 `\r\n` 匹配失败

### 错误 2：`read_file` 返回的行号与文件实际行数对不上

**现象：**
- 例如 `read_file` 返回标称 500 行，但实际文件在编辑器里看到 500 行
- 这在 `\r\n` 下影响不大，但行号完全准确时需要小心

## 优化建议

### 方案 A：配置 Git 换行符（推荐，一劳永逸）

```bash
# 让 Git 保持 LF（Linux 风格），不再自动转 CRLF
git config --global core.autocrlf input
```

然后重新 clone 或 checkout 项目，所有文件都会是 `\n` 结尾，`edit_file` 就不会匹配失败了。

### 方案 B：项目级 `.gitattributes`（不影响全局）

在项目根目录添加 `.gitattributes`：

```
* text=auto eol=lf
```

这样无论开发者在什么平台，Git 都强制用 LF 换行符。

### 方案 C：不改换行符，工具侧适配（较复杂）

如果必须保留 `\r\n`，可以在工具查找/替换前做归一化处理。但从工具实现角度，更建议源头解决。

## 总结

| 问题 | 根因 | 最优解法 |
|------|------|---------|
| `edit_file` 匹配失败 | 文件 `\r\n` ≠ 参数 `\n` | 配置 `core.autocrlf input` |
| 其他 whitespace 不匹配 | 缩进/空格差异 | 粘贴代码前确保格式一致 |
